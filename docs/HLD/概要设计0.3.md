#### 4.2.1 缓存策略

| 数据类型 | 缓存策略 | 过期时间 | 一致性方案 |
|----------|----------|----------|------------|
| 书籍详情 | Cache-Aside | 30分钟 | 更新时删除缓存 |
| 书籍列表 | Cache-Aside | 5分钟 | 定时刷新 |
| 用户权限 | Cache-Aside | 10分钟 | 变更时删除缓存 |
| 账户余额 | Cache-Aside | 5分钟 | 变更时删除缓存 |
| 热门排行 | Read-Through | 1小时 | 定时计算刷新 |
| 系统配置 | Read-Through | 永久 | Nacos推送更新 |
| 计费配置 | Read-Through | 永久 | Nacos推送更新 |

#### 4.2.2 缓存策略选择说明

**为什么部分场景使用 Read-Through 策略？**

Read-Through 策略的核心特点是：**缓存层对应用透明，应用只与缓存层交互，缓存层负责在缓存未命中时自动从数据源加载数据**。

| 策略 | 适用场景 | 本项目应用 |
|------|----------|------------|
| **Cache-Aside** | 数据更新频繁、需要强一致性 | 书籍详情、用户权限、账户余额 |
| **Read-Through** | 数据更新少、读取频繁、可接受最终一致性 | 热门排行、系统配置、计费配置 |

**选择 Read-Through 的原因：**

1. **热门排行榜**：由定时任务计算生成，更新频率固定（每小时），应用层无需关心加载逻辑，缓存层自动从定时任务结果加载
2. **系统配置**：通过Nacos推送更新，配置变更频率极低，适合Read-Through模式，配置变更时主动刷新缓存
3. **计费配置**：与系统配置类似，变更频率低，通过Nacos管理，适合Read-Through模式

**优势：**
- 应用代码更简洁，无需处理缓存加载逻辑
- 缓存层统一管理数据加载，便于监控和维护
- 适合"写少读多"的场景，减少数据库压力

#### 4.2.3 缓存一致性保证

1. **Cache-Aside模式**：读时先查缓存，未命中再查数据库并写入缓存；写时先更新数据库，再删除缓存
2. **延迟双删**：更新数据库后删除缓存，延迟1秒再删除一次，防止并发问题
3. **缓存预热**：系统启动时加载热点数据到缓存
4. **缓存穿透防护**：布隆过滤器过滤不存在的key
5. **缓存击穿防护**：互斥锁（分布式锁）防止缓存失效时大量请求打到数据库
6. **缓存雪崩防护**：缓存过期时间加随机值，避免同时失效

### 4.5 书籍上传与格式转换

#### 4.5.1 支持的上传格式

| 格式 | 扩展名 | 说明 |
|------|--------|------|
| 纯文本 | .txt | 纯文本格式，最简单，直接解析 |
| PDF | .pdf | 便携式文档格式，需提取文本内容 |
| Word 97-2003 | .doc | 旧版Word格式，需转换库解析 |
| Word 2007+ | .docx | 新版Word格式（XML），相对容易解析 |

**注意**：系统仅接受以上四种格式，其他格式在上传时直接拒绝。

#### 4.5.2 上传与转换流程

```
管理员上传书籍文件
       │
       ▼
book-service 接收文件
       │
       ▼
校验文件格式（仅允许 txt/pdf/doc/docx）
       │ 格式不符 → 返回错误
       │
       ▼
将原始文件上传到 AWS S3（original.{ext}）
       │
       ▼
发送异步消息到 Kafka（book.parse.topic）
       │
       ▼
book-service 异步消费消息
       │
       ▼
根据文件格式选择解析器：
  - .txt → 直接按段落分割
  - .pdf → 使用 Apache PDFBox 提取文本
  - .doc → 使用 Apache POI 提取文本
  - .docx → 使用 Apache POI (XWPF) 提取文本
       │
       ▼
生成 EPUB 格式文件：
  1. 提取文本内容并按章节/段落分割
  2. 生成 EPUB 的 OPF、NCX、HTML 等文件
  3. 打包为 .epub 文件
       │
       ▼
将 EPUB 文件上传到 AWS S3（content.epub）
       │
       ▼
提取前 10% 内容生成 preview.epub（试读）
       │
       ▼
解析章节信息，生成 metadata.json
       │
       ▼
更新书籍状态为"已上架"，同步 ES 索引
```

#### 4.5.3 技术实现

| 组件 | 技术 | 说明 |
|------|------|------|
| PDF 解析 | Apache PDFBox | 提取PDF文本内容、页码信息 |

| 异常场景 | 处理策略 |
|----------|----------|
| 文件格式不支持 | 上传时直接拒绝，返回错误提示 |
| 文件解析失败 | 记录错误日志，发送告警通知，书籍状态标记为"解析失败" |
| EPUB 生成失败 | 重试3次，仍失败则标记为"转换失败"，通知管理员 |
| S3 上传失败 | 重试机制，记录错误日志 |

### 4.6 在线阅读性能策略

| 策略 | 说明 |
|------|------|
| 按页/按章节加载 | 不一次性加载整本书，按需获取 |
| CDN 缓存 | 热点书籍内容通过 CDN 分发 |
| 预加载 | 用户阅读当前页时，预加载下一页 |
| 内容格式转换 | 建议将 EPUB 转换为 HTML 分片【空间换时间】，便于 Web 阅读 |
| 本地缓存 | 用户阅读进度缓存到本地 |

### 4.7 阅读进度与历史存储策略

#### 4.7.1 阅读进度存储

| 存储类型 | 用途 | 说明 |
|----------|------|------|
| Redis | 实时阅读进度 | Key: `elibrary:reading:progress:{userId}:{bookId}`，TTL 90天 |
| 本地缓存 | 当前会话进度 | Caffeine缓存，避免频繁读写Redis |

#### 4.7.2 阅读历史存储

| 存储类型 | 用途 | 说明 |
|----------|------|------|
| MySQL | 持久化阅读历史 | t_reading_history表，记录每次阅读行为 |

**阅读历史表结构：**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT | 主键 |
| user_id | BIGINT | 用户ID |
| book_id | BIGINT | 书籍ID |
| page_number | INT | 阅读页码 |
| chapter | VARCHAR | 阅读章节 |
| read_time | DATETIME | 阅读时间 |
| duration | INT | 阅读时长（秒） |
| created_at | DATETIME | 创建时间 |

#### 4.7.3 进度同步流程

```
用户阅读页面
       │
       ▼
前端每翻一页/每30秒发送进度更新请求
       │
       ▼
read-service接收请求
       │
       ▼
更新Redis进度（主存储）
       │
       ▼
异步写入MySQL阅读历史（持久化）
       │
       ▼
下次打开书籍时，从Redis读取进度
       │ 未命中 → 从MySQL读取最近一次进度
       │ 均未命中 → 从第1页开始
```

#### 4.7.4 阅读历史查询流程

```
用户查看阅读历史
       │
       ▼
read-service接收请求
       │
       ▼
查询MySQL阅读历史表
       │ WHERE user_id = ?
       │ ORDER BY read_time DESC
       │
       ▼
返回阅读历史列表
（书籍信息、阅读时间、阅读页码、阅读时长）
```

## 8. 鉴权与MDC设计

### 8.1 鉴权架构

```
┌──────────┐     ┌──────────────┐     ┌──────────────┐
│  客户端   │────▶│  API 网关     │────▶│  业务服务     │
│          │     │  JWT校验      │     │  MDC获取      │
└──────────┘     └──────────────┘     └──────────────┘
```

### 8.2 鉴权流程

#### 8.2.1 Web接口鉴权（真实客户）

1. 客户端携带JWT Token发起请求
2. API网关校验Token有效性
3. 从Token中解析用户ID和用户类型（NORMAL/VIP）
4. 将`userId`和`userType`写入MDC
5. 请求转发到业务服务
6. 业务服务通过MDC获取当前用户信息
7. 请求完成后清除MDC

#### 8.2.2 BOS接口鉴权（管理员）

1. 管理员携带JWT Token发起请求
2. API网关校验Token有效性
3. 从Token中解析管理员ID和角色
4. 将`adminId`和`adminRole`写入MDC
5. 请求转发到业务服务
6. 业务服务通过MDC获取当前管理员信息
7. 请求完成后清除MDC

### 8.3 MDC字段定义

| 字段 | 说明 | Web接口 | BOS接口 |
|------|------|---------|---------|
| traceId | 全局追踪ID | ✓ | ✓ |
| userId | 真实客户ID | ✓ | - |
| userType | 客户类型（NORMAL/VIP） | ✓ | - |
| adminId | 管理员ID | - | ✓ |
| adminRole | 管理员角色 | - | ✓ |

### 8.4 日志格式

```
%d{yyyy-MM-dd HH:mm:ss} [%thread] [%X{traceId}] [%X{userId}] [%X{adminId}] %-5level %logger{36} - %msg%n
```

```
┌─────────────┐     ┌─────────────┐
│   Master    │────▶│   Slave 1   │
│  (读写)     │     │  (只读)     │
└──────┬──────┘     └─────────────┘
       │
       ▼
┌─────────────┐     ┌─────────────┐
│   MHA       │────▶│   Slave 2   │
│  (监控+切换) │     │  (只读)     │
└─────────────┘     └─────────────┘
```

**MHA（Master High Availability）工作原理：**

1. **监控**：MHA Manager 持续监控 Master 节点健康状态
2. **故障检测**：当 Master 节点宕机或网络不可达时，MHA 在 10-30 秒内检测到故障
3. **自动切换**：
   - 选择数据最新的 Slave 作为新 Master
   - 将其他 Slave 重新指向新 Master
   - 更新 VIP（虚拟IP）或 DNS 指向新 Master
4. **应用透明**：通过 VIP 或连接中间件，应用无需修改连接配置

**优势：**
- 自动故障切换，减少人工干预
- 切换时间短（10-30秒）
- 数据一致性高（基于binlog位置选择新Master）

### 10.3 服务保护

| 策略 | 说明 |
|------|------|
| **限流** | **令牌桶算法（Sentinel）**，限制QPS，支持突发流量 |
| 熔断 | 错误率超过阈值自动熔断（Sentinel） |
| 降级 | 关键服务故障时返回缓存或默认数据 |
| 超时 | 设置合理的请求超时时间 |
| 重试 | 幂等操作支持自动重试 |

#### 10.3.1 令牌桶限流机制

```
┌─────────────┐
│  令牌桶      │
│  容量: 1000  │
│  速率: 100/s │
└──────┬──────┘
       │
       ▼
   请求到达
       │
       ├─ 有令牌 → 放行
       │
       └─ 无令牌 → 拒绝/排队
```

**为什么选择令牌桶算法？**

| 算法 | 特点 | 适用场景 |
|------|------|----------|
| **令牌桶** | 允许突发流量（桶中有令牌时可快速处理），平滑限流 | **Web API、突发流量场景** |
| 漏桶 | 严格限制速率，不允许突发流量 | 固定速率处理场景 |
| 计数器 | 简单但存在临界问题 | 简单限流场景 |

**Sentinel 令牌桶配置示例：**

| 接口 | QPS限制 | 突发容量 | 拒绝策略 |
|------|---------|----------|----------|
| 书籍列表 | 500 | 1000 | 快速失败 |
| 书籍详情 | 1000 | 2000 | 快速失败 |
| 借阅接口 | 200 | 500 | 排队等待 |
| 支付接口 | 100 | 200 | 快速失败 |
| 搜索接口 | 300 | 600 | 快速失败 |

#### 11.2.1 为什么使用 Filebeat + Logstash + ES 而不是 ELK？

**说明：ELK 本身就是 Elasticsearch + Logstash + Kibana 的缩写，而本方案使用的是 Filebeat + Logstash + Elasticsearch，区别在于：**

| 方案 | 组件 | 说明 |
|------|------|------|
| **本方案** | Filebeat + Logstash + Elasticsearch | 轻量级日志采集 |
| 完整 ELK | Filebeat + Logstash + Elasticsearch + **Kibana** | 包含可视化查询界面 |

**为什么日志采集层不使用 Kibana？**

1. **职责分离**：Kibana 是数据可视化工具，不属于日志采集链路，而是日志查询和展示层
2. **架构清晰**：采集层（Filebeat）→ 处理层（Logstash）→ 存储层（Elasticsearch）→ 展示层（Kibana）
3. **实际使用**：Kibana 仍然会部署，但用于日志查询和告警面板展示，不属于采集链路

**为什么使用 Filebeat 而不是直接 Logstash？**

| 组件 | 资源消耗 | 部署位置 | 职责 |
|------|----------|----------|------|
| **Filebeat** | 极低（Go语言） | 每个应用节点 | 轻量级日志采集和转发 |
| Logstash | 较高（JVM） | 集中部署 | 日志解析、过滤、转换 |

**优势：**
- Filebeat 资源消耗极低，适合部署在每个应用节点
- Logstash 集中处理，避免每个节点都运行JVM
- 架构更清晰，职责分离

### 11.4 告警规则

| 告警级别 | 触发条件 | 通知渠道 |

### 11.5 告警查重机制

为避免频繁发送相同告警导致用户反感，系统实现告警查重机制：

#### 11.5.1 告警指纹

每条告警生成唯一指纹，用于标识同类告警：

```
告警指纹 = MD5(告警类型 + 目标用户ID + 告警原因)
```

| 告警类型 | 指纹组成 | 示例 |
|----------|----------|------|
| 余额不足提醒 | `alert:balance_low:{userId}` | `alert:balance_low:10001` |
| 强制归还 | `alert:force_return:{userId}` | `alert:force_return:10001` |
| VIP到期提醒 | `alert:vip_expiry:{userId}` | `alert:vip_expiry:10001` |
| 支付失败 | `alert:payment_failed:{orderId}` | `alert:payment_failed:ORD20260924001` |

#### 11.5.2 静默窗口

同一告警指纹在静默窗口内不重复发送：

| 告警类型 | 静默窗口 | 说明 |
|----------|----------|------|
| 余额不足提醒 | 24小时 | 每天最多提醒1次 |
| 强制归还 | 24小时 | 每天最多提醒1次 |
| VIP到期提醒 | 7天 | 每周最多提醒1次 |
| 支付失败 | 1小时 | 每小时最多提醒1次 |

#### 11.5.3 升级策略

若静默窗口内告警持续存在，超过阈值后升级为高级别告警：

| 告警类型 | 升级阈值 | 升级后动作 |
|----------|----------|------------|
| 余额不足 | 连续3天余额不足 | 升级为P1告警，通知管理员 |
| 支付失败 | 连续3次支付失败 | 升级为P1告警，通知管理员 |
| VIP到期 | 到期后7天未续期 | 发送最终提醒 |

#### 11.5.4 技术实现

```
告警触发
   │
   ▼
生成告警指纹
   │
   ▼
查询Redis是否已存在该指纹
   │
   ├─ 存在 → 检查是否在静默窗口内
   │         │
   │         ├─ 在静默窗口内 → 跳过发送
   │         │
   │         └─ 超出静默窗口 → 检查升级阈值
   │                           │
   │                           ├─ 未达阈值 → 发送告警，更新指纹
   │                           │
   │                           └─ 达到阈值 → 升级告警，通知管理员
   │
   └─ 不存在 → 发送告警，写入Redis（设置TTL）
```

**Redis存储结构：**

```
Key: alert:fingerprint:{fingerprint}
Value: JSON {
  "count": 3,           // 触发次数
  "firstTime": "2026-09-24T10:00:00",  // 首次触发时间
  "lastTime": "2026-09-24T10:30:00",   // 最后触发时间
  "status": "silenced"  // 状态：active/silenced/escalated
}
TTL: 根据告警类型设置（24小时/7天等）
```

## 12. 并发与一致性策略

### 12.1 评论并发

- 多用户同时评论同一本书：数据库事务 + 乐观锁（version 字段）
- 评论总数统计：使用计数器字段，避免每次 COUNT
- 缓存更新：评论后删除书籍详情缓存

### 12.2 借阅并发

- 同一用户同时借阅同一本书：唯一索引约束（userId + bookId）+ 分布式锁
- 借阅上限校验：在事务中完成查询与插入
- 幂等性保证：使用请求ID或业务唯一键

### 12.3 书籍状态更新并发

- 上下架操作：Redis分布式锁 + 数据库乐观锁
- 锁续期：WatchDog自动续期防止锁超时
- 缓存同步：更新后删除缓存，下次请求重新加载

### 12.4 备注并发

- 同一用户对同一页添加多条备注：允许，通过时间戳排序
- 分布式锁保护同一用户同一页的备注操作
- 权限控制：仅创建者和管理员可查看

### 12.5 支付并发

- 支付回调幂等：使用订单号作为唯一键
- 对账任务分布式锁：防止多实例重复执行
- 订单状态机：严格的状态流转控制

### 12.6 余额扣减并发

- 余额扣减：Redis分布式锁 + 数据库乐观锁
- 防止余额为负：扣减前校验余额充足
- 幂等性保证：使用请求ID

### 12.7 强制归还并发

- 定时任务扫描余额不足用户，使用分布式锁防止重复执行
- 强制归还操作使用独立线程池
- 归还后发送通知提醒用户

## 14. 核心业务流程

### 14.1 借阅续期流程

#### 14.1.1 续期规则

| 用户类型 | 续期次数限制 | 每次续期时长 | 计费方式 |
|----------|-------------|-------------|----------|
| 普通用户（Normal） | 最多2次 | 每次7天 | 按续期天数×日费率 |
| VIP用户 | 最多2次 | 每次15天 | 按续期天数×日费率（可配置折扣） |

#### 14.1.2 续期前置条件

- 未达续期次数上限
- 账户余额充足
- 借阅未过期（或已过期但未归还）

#### 14.1.3 续期流程

```
用户发起续期请求
       │
       ▼
校验续期条件：
  1. 借阅记录是否存在
  2. 是否已达续期次数上限
  3. 账户余额是否充足
       │ 任一不满足 → 返回错误
       │
       ▼
计算续期费用：
  - 续期天数 × 日费率 × 折扣（如有）
       │
       ▼
扣减账户余额（分布式锁保护）
       │
       ▼
更新借阅记录：
  - 到期时间延长
  - 续期次数+1
  - 记录续期费用
       │
       ▼
返回续期成功
```

### 14.2 VIP自动续期流程

#### 14.2.1 自动续期规则

- 用户需主动开通自动续期功能
- 自动续期在VIP到期前1天执行
- 自动续期扣费失败则不续期，VIP正常降级
- 自动续期成功后，VIP有效期累加

#### 14.2.2 自动续期流程

```
定时任务扫描（每天执行）
       │
       ▼
查询开通自动续期且7天内到期的VIP用户
       │
       ▼
对每个用户：
  1. 检查账户余额是否充足
  2. 余额充足 → 扣费 → 延长VIP有效期
  3. 余额不足 → 发送余额不足提醒
       │
       ▼
记录续期结果
```

### 14.3 对账流程

#### 14.3.1 对账规则

- 每日凌晨2点执行对账任务
- 对比本地订单记录与支付平台订单记录
- 发现差异时生成对账报告
- 异常订单自动或人工处理

#### 14.3.2 对账流程

```
定时任务触发（每天2点）
       │
       ▼
获取昨日所有订单记录
       │
       ▼
调用支付平台API获取昨日订单
       │
       ▼
逐条比对订单：
  - 订单号
  - 订单金额
  - 订单状态
  - 支付时间
       │
       ▼
发现差异：
  - 本地有，支付平台无 → 可能支付失败
  - 本地无，支付平台有 → 可能回调丢失
  - 金额不一致 → 异常订单
       │
       ▼
生成对账报告
       │
       ▼
差异超过阈值 → 发送告警
```

#### 14.3.3 对账报告

| 字段 | 说明 |
|------|------|
| 对账日期 | 对账的日期 |
| 本地订单数 | 本地系统记录的订单数 |
| 支付平台订单数 | 支付平台记录的订单数 |
| 一致订单数 | 两边一致的订单数 |
| 差异订单数 | 两边不一致的订单数 |
| 差异金额 | 差异订单的总金额 |
| 差异类型 | 本地多/支付平台多/金额不一致 |
| 处理状态 | 未处理/处理中/已处理 |

### 15.2 核心设计决策

1. **借阅 = 权限，非库存**：电子书无数量限制，借阅是开通阅读权限
2. **试读与全文分离**：试读内容独立存储，无需权限即可访问
3. **评论公开，备注私有**：权限模型完全不同
4. **文件与元数据分离**：数据库只存元数据和URL，文件存对象存储
5. **Web 与 BOS 分离**：两套 Controller，权限模型清晰
6. **真实客户与管理员分离**：两类用户群体分开管理，不可混为一谈
7. **缓存优先**：热点数据优先走缓存，降低数据库压力
8. **异步处理**：非核心逻辑异步化，提升响应速度
9. **幂等设计**：所有写操作支持幂等，防止重复提交
10. **分布式锁**：关键资源操作使用分布式锁保护
11. **可观测性**：全链路监控，问题快速定位
12. **gRPC用于微服务间**：Web与BOS间不需要gRPC，gRPC用于微服务间高性能通信
13. **ES全文搜索**：电子书内容索引到ES，支持全文检索
14. **Nacos统一服务发现与配置**：避免引入过多组件，降低运维复杂度
15. **线程池优化**：高并发场景使用线程池，支持动态调整和监控
16. **借阅计费**：按日计费，支持余额扣减
17. **书籍权限配置**：支持VIP免费/VIP付费/公开免费/公开付费
18. **借阅续期**：支持用户续期借阅，按续期天数计费
19. **余额不足强制归还**：定时扫描，余额不足时强制归还所有借阅
20. **全接口鉴权**：Web和BOS接口均需鉴权，鉴权后信息写入MDC
21. **SkyWalking链路追踪**：功能强大，支持日志关联、性能分析、拓扑图展示
22. **Sentinel限流熔断**：令牌桶算法，支持突发流量，服务保护
23. **MySQL主从+MHA**：自动故障切换，保障数据高可用
24. **AWS S3对象存储**：高持久性，多可用区冗余
25. **书籍格式转换**：支持txt/pdf/doc/docx上传，自动转换为EPUB存储
26. **告警查重**：基于告警指纹+静默窗口，避免频繁发送相同告警
27. **阅读历史**：记录用户阅读行为，支持快速继续阅读
28. **数据看板**：提供运营数据支撑，辅助决策
29. **对账功能**：保障财务安全，发现异常订单
30. **VIP自动续期**：提升用户体验，减少手动操作

### 15.3 已知风险

| 风险 | 影响 | 应对 |
|------|------|------|
| **电子书格式解析复杂** | **PDF/DOC解析需要额外依赖，转换质量不可控** | **使用成熟开源库（PDFBox/POI），转换失败时重试并告警** |
| **对象存储集成耗时** | **S3 SDK 接入需要时间** | **初版用本地文件系统抽象接口，后续切换S3** |
| 权限校验遗漏 | 未借阅用户可能访问全文 | 统一拦截器 + Service 层双重校验 |
| 分布式事务复杂度高 | 跨服务一致性难保证 | 优先使用最终一致性，避免强一致性 |
| 缓存一致性难保证 | 缓存与数据库数据不一致 | Cache-Aside + 延迟双删 + 定时校对 |
| 消息丢失 | Kafka消息丢失导致业务异常 | 消息持久化 + 确认机制 + 死信队列 |
| ES索引同步延迟 | 书籍更新后搜索不到最新内容 | 实时同步 + 定时全量校对 |
| 余额并发扣减 | 并发扣减可能导致余额为负 | 分布式锁 + 乐观锁 + 事务 |
| 强制归还误判 | 余额计算误差导致误归还 | 强制归还前二次确认，记录详细日志 |
| **告警查重失效** | **用户收到重复告警** | **Redis分布式存储，确保多实例共享状态** |
| **对账数据不一致** | **财务数据不准确** | **多轮对账+人工复核，异常订单标记处理** |
